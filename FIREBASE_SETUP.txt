🔧 Firebase Setup - Step by Step Guide
═════════════════════════════════════════════════════════════════

What this replaces
────────────────────
Right now the site saves everything in the browser's localStorage
(articles, tracking codes, the Sheets webhook URL). That means an
edit made on one computer never shows up for other visitors.
Firebase turns this into a real, shared database — every visitor
sees the same content, from any device.

What will be stored in Firebase (4 parts)
────────────────────────────────────────────
1. Articles (replaces localStorage key "pulsar_articles")
2. Newsletter signups (the "want the best articles by email?" form
   — right now it doesn't actually save anything!)
3. Form/lead submissions from inside articles (forms with
   class="sheets-form")
4. Tracking codes & settings (GTM, FB Pixel, GA4, Hotjar, etc.)

Step 1: Create a Firebase project
────────────────────────────────────
1. Go to https://console.firebase.google.com/
2. Click "Add project" → give it a name, e.g. "israel-magazine"
3. You can turn off Google Analytics at this step (not needed)
4. Click "Create project"

Step 2: Add a Web app
─────────────────────────
1. On the project page → click the Web icon ( </> )
2. Give the app a nickname (e.g. "israel-magazine-web")
3. You don't need Firebase Hosting at this step
4. Click "Register app"
5. Firebase will show you a config object that looks like this:

   const firebaseConfig = {
     apiKey: "AIzaSy...",
     authDomain: "israel-magazine-xxxxx.firebaseapp.com",
     projectId: "israel-magazine-xxxxx",
     storageBucket: "israel-magazine-xxxxx.appspot.com",
     messagingSenderId: "123456789",
     appId: "1:123456789:web:abcdef123456"
   };

   *** Copy this whole object and send it to me — I'll plug it
       into js/firebase-config.js in place of the placeholder
       values that are there now. ***

Step 3: Enable Realtime Database
────────────────────────────────────
1. In the left sidebar → Build → Realtime Database
2. Click "Create Database"
3. Choose a location (Belgium/europe-west1 is recommended —
   closest region to Israel)
4. Start in "Test mode" (open access) — we'll lock this down
   later (see "Security" below — this is critical to do
   *before* the site goes live)
5. Once created, copy the URL shown at the top
   (it looks like: https://israel-magazine-xxxxx-default-rtdb.
   europe-west1.firebasedatabase.app)
   *** Send me this URL too — it's the databaseURL in the config ***

Step 4: Data structure that will be created automatically
────────────────────────────────────────────────────────────
/articles/{id}          → each article (same shape as localStorage had)
/newsletter/{id}         → { email, timestamp }
/leads/{id}              → { formName, name, phone, email, q1..q5, timestamp, articleId }
/settings/codes          → { gtm, fb, ga, hj, tb, ob, custom }

Step 5: Security (important — before the site goes live!)
───────────────────────────────────────────────────────────
"Test mode" lets anyone on the internet read AND write to the
database — that's fine for testing, but dangerous for a live site
(anyone could delete every article from their own browser).
Before launch, we need to update the database Rules so that
articles are readable by everyone, but writing (adding/editing
articles) requires admin authentication. I'll set this up when we
get to that step — just remind me.

Step 7: Database Rules + admin login  (done — Sep 2026)
─────────────────────────────────────────────────────────────────
Why this was needed: the database was still on "Test mode" rules,
which carry a hardcoded expiry date. That date passed, the rules
flipped to deny-all, and every page broke at once — articles stopped
loading (permission_denied at /articles) and js/code-injector.js
could no longer read /settings/codes, so GTM and all the tracking
pixels stopped firing too.

The rules now live in the repo at firebase-database-rules.json.
To apply: Firebase Console -> Realtime Database -> Rules ->
paste the file contents -> Publish. No expiry date, so this
cannot silently break again.

What the rules allow:
  articles                     public read, admin-only write
  settings/codes               public read (code-injector needs it
  settings/thankYouPage        on every page load), admin-only write
  settings/sheetsWebhookUrl
  settings/manhattanSheetsWebhookUrl
  leads                        anyone may CREATE a new lead (the
                               forms), only admin may read/delete
  newsletter                   same as leads
  everything else              admin only

"admin" is NOT simply "any signed-in user". The API key in
js/firebase-config.js is public (the site needs it), so once the
Email/Password provider is on, anyone holding that key could register
themselves an account. A rule of "auth != null" would hand them the
whole database. So the rules name one specific account by its UID:

  auth.uid === '6boNPG3JnjUjXWHnJUGUSEr8cXz2'

That UID is not a secret and grants nothing on its own — without the
account password it is only an identifier.

Creating the admin account (one time):
  1. Authentication -> Sign-in method -> enable Email/Password
  2. Authentication -> Settings -> User actions -> UNCHECK
     "Enable create (sign-up)"   <- blocks public self-registration
  3. Authentication -> Users -> Add user -> pick the email + password
     (this is the login; there is no default password in the code)
  4. Copy the User UID into firebase-database-rules.json
  5. Realtime Database -> Rules -> paste that file -> Publish

To add a second admin later, change the rule to
  auth.uid === '<uid one>' || auth.uid === '<uid two>'
and Publish again. No node needs to be created in the data tree.

The login screen itself is js/admin-auth.js, loaded by the five
admin pages that touch the database (index, code-manager,
thank-you-editor, leads, newsletter). It must stay loaded straight
after js/firebase-config.js and before each page's own script —
creating firebase.auth() first is what makes the Realtime Database
SDK wait for the auth token instead of firing off unauthenticated
reads that come back permission_denied.

Note that the login screen is convenience, not security: it can be
bypassed in DevTools. The actual protection is the rules above —
without a signed-in user the server returns nothing.

OPEN ITEM — statusAppConfig / statusAppLeads
─────────────────────────────────────────────────────────────────
These two nodes exist in the database but are not referenced
anywhere in this codebase — they belong to some other app. The
rules deliberately leave them open (read+write for everyone),
which is exactly how they already were under the old Test mode
rules, so publishing cannot break whatever uses them.

That is a placeholder, not a decision. statusAppLeads may well
hold personal data, and right now anyone with the database URL
can read it. Once we know what owns these nodes, tighten them the
same way /leads is tightened.
